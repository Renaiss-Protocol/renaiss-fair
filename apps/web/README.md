# web — Renaiss Fair-Play Verifier

A Next.js app where anyone can verify that a gacha pack rip provably resolved
to the card received.

Routes (`/` redirects to `/trace-a-rip`; a verified tx is carried in `?tx=` so
switching routes — or sharing the link — restores the whole verification):

- **`/trace-a-rip`** (landing): the "Every rip. Provably yours." hero feeds an
  interactive prover — the user clicks through every derivation (on-chain
  facts → α → ECVRF_verify → index → card), all crypto executed in the
  browser on click, with a **provenance hover on every datum** (green =
  on-chain, amber = API, white = computed locally, red = on-chain pending)
- **`/behind-the-rip`**: how each set is formed — every set as a row, newest
  first; expand for the full lineup, the recomputed Merkle root against the
  on-chain commitment, and a replay of the packing run that built it, attempt
  by attempt, using `@renaiss/algorithms`
- **`/whitepaper`**: the protocol whitepaper in a light reading theme. A
  floating bottom-right button transitions the site between the dark verifier
  and the light paper via a circular reveal; the sticky TOC scroll-spies.
- **`/faq`**: straight answers on what is provable today and what still
  requires trust
- **`/flow-diagram`**, **`/story`**, **`/tamper`**: exploratory
  visualizations, hidden behind `NEXT_PUBLIC_SHOW_FLOW` /
  `NEXT_PUBLIC_SHOW_STORY` / `NEXT_PUBLIC_SHOW_TAMPER` (unset ⇒ 404 + hidden
  from nav). `NEXT_PUBLIC_SHOW_DESIGN_CONFIG` exposes the whitepaper palette
  switcher. All flags are off by default (see `lib/flags.ts`).

## The verification is real

Every draw's ECVRF proof is verified **in the browser** with the RFC 9381
implementation in [`packages/ecvrf`](../../packages/ecvrf)
(ECVRF-EDWARDS25519-SHA512-ELL2, suite 0x04), through the draw pipeline in
[`packages/verifiable-draw`](../../packages/verifiable-draw):

- α = `keccak256(tag ‖ blockHash ‖ onChainPackId ‖ checkoutId as 32-byte BE)`
  (the UTF-8 domain-separation tag scopes the seed hash to this draw formula;
  the bytes32 pack id makes the seed globally unique — checkoutId alone is
  only unique per pack)
- `ECVRF_verify(PK, α, π)` → β must equal the stored `randomness`
- card index = `keccak256(β) mod remaining`, sampled **without replacement**
  over the lineup sorted by token ID ASC, draws in `checkoutId` order
- the replayed pick must equal the recorded resolution

See `lib/verify.ts` — it mirrors the production resolver exactly. Set
formation is replayed the same way: `lib/merkle.ts` recomputes each set's
Merkle root from the served lineup and compares it with the root committed
on-chain (the vending-machine contract's `merkleRoots(packId, setId)`), and
the packing view re-runs the Fair Set Adaptive Algorithm from the recorded
seed and config.

## Data sources

The data source is switched by `NEXT_PUBLIC_RENAISS_API_URL` (see
`lib/config.ts` and `.env.example`):

- **Set** ⇒ the app reads the public, unauthenticated Renaiss fair-play API.
  Give it the bare host (no path); the `/vN/fair` route prefix and every
  endpoint live in `lib/api/renaiss/verify/` (`http.ts` holds the prefix —
  `/v1/fair` is the current surface, `/v0/fair` its deprecated predecessor).
  In API mode, `NEXT_PUBLIC_RPC_URL` + `NEXT_PUBLIC_TVM_ADDRESS` additionally
  point the "published root" chip at the vending-machine contract's
  on-chain `merkleRoots` commitment (unset ⇒ it compares the
  API-served root and says so).
- **Unset** (default) ⇒ `lib/api/client.ts` serves the committed demo world in
  `lib/api/fixtures.json`: two packs, generated by `pnpm generate-fixtures`
  with a **real ECVRF keypair and real proofs**, so verification legitimately
  passes — nothing about the math is faked, only the transport.

Like all `NEXT_PUBLIC_*` vars these are inlined at build time — the static
export has no runtime toggle.

A few things to know about the API:

- Sets appear only after they are **complete** and after a **delay**; an
  active set's remaining lineup is never served, so nothing on this site can
  tell a buyer what is left in a pack.
- Requests are rate limited.
- The demo secret key in `app/packing/page-client.tsx` (`DEMO_SK`) is the
  published RFC 8032 §7.1 test vector, used only so the in-browser packing
  demo can prove and verify with a deterministic key. No operator secret key
  exists anywhere in this repo; production runs return the operator's π and
  the app only ever verifies.

## Run

```bash
pnpm install
pnpm dev                 # dev server on port 3000 — use the "Use Demo Rip" button
pnpm generate-fixtures   # optional: reroll the demo world (new keypair + proofs)
```

Design tokens follow the renaiss.xyz design system (dark stage, gradient
outline primaries, Poppins/Manrope, tier color ladder), expressed as a
Tailwind CSS v4 `@theme` in `app/globals.css`. Animations use GSAP
(`useGSAP`, timelines); `prefers-reduced-motion` skips straight to the
verified result.
